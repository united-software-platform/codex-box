Окружение для изолированного запуска Codex в Docker-контейнере. Агент работает только внутри
каталога проекта, под выбранным профилем и с собственными SSH-ключом и авторизацией `gh`.
В образе только агент и инструменты работы с репозиторием, без правил, методологий и прочих надстроек.

## Зачем

- **Изоляция файловой системы.** В контейнер монтируется только рабочее дерево проекта. Домашний каталог
  хоста, соседние репозитории и системные настройки агенту недоступны.
- **Несколько аккаунтов без перелогина.** Каждый профиль хранит авторизацию и конфиг Codex в своём
  каталоге `.codex-accounts/<профиль>`. Профиль переключается переменной в команде запуска.
- **Свои ключ и `gh` у проекта.** SSH-ключ лежит в `.ssh/`, авторизация GitHub CLI — в `.gh/`.
  Оба каталога монтируются в контейнер, ключи и токены хоста не задействованы.
- **Файлы остаются вашими.** Контейнерный пользователь `codex` имеет UID/GID `1000:1000`, поэтому
  созданные агентом файлы не оказываются во владении `root`.

---

## Требования

Docker с плагином `docker compose` версии 2.24 или новее и `ssh-keygen`.

## Подключение к проекту

### 1. Добавить сервис в compose-файл

В `docker-compose.yml` проекта, к которому подключается агент, добавляется сервис. Он использует готовый
образ из GHCR, сборка не нужна:

```yaml
services:
  codex:
    image: ghcr.io/united-software-platform/codex-box:latest
    # Отдельный compose-профиль: `docker compose up` агента не поднимает
    profiles: ["codex"]
    # Команда по умолчанию — сам агент; аргумент после имени сервиса её заменяет (bash, git, gh)
    command: codex
    working_dir: ${PROJECT_DIR:-/app}
    # Значения .env доступны агенту переменными; сам файл необязателен
    env_file:
      - path: .env
        required: false
    environment:
      # Конфиг и авторизация Codex живут в каталоге профиля
      CODEX_HOME: ${CODEX_HOME:-/home/codex/.codex}
      # Авторизация gh живёт в каталоге .gh проекта
      GH_CONFIG_DIR: ${GH_CONFIG_DIR:-/home/codex/.config/gh}
    volumes:
      - .:${PROJECT_DIR:-/app}                                                # рабочее дерево проекта
      # Профиль обязателен: без него путь схлопнулся бы в каталог всех профилей
      - ${CODEX_ACCOUNTS_DIR:-.codex-accounts}/${CODEX_PROFILE:?не задан профиль аккаунта Codex}:${CODEX_HOME:-/home/codex/.codex}
      - ${PROJECT_DIR:-/app}/${CODEX_ACCOUNTS_DIR:-.codex-accounts}           # анонимный том прячет чужие профили
      - ${SSH_DIR:-.ssh}:/home/codex/.ssh                                     # ключ для работы с репозиторием
      - ${GH_DIR:-.gh}:${GH_CONFIG_DIR:-/home/codex/.config/gh}               # авторизация gh
      # Файл секретов скрыт от агента: compose читает его на хосте, а внутри контейнера он пуст
      - /dev/null:${PROJECT_DIR:-/app}/.env:ro
```

Смысл ключевых параметров:

- `image` — готовый мультиарх-образ из GHCR. Тег `latest` указывает на последнюю опубликованную сборку,
  конкретная версия Codex закрепляется тегом версии — см. [Версионирование образа](#версионирование-образа);
- `profiles: ["codex"]` — агент не поднимается вместе с сервисами проекта по `docker compose up`;
- `CODEX_HOME` — Codex хранит авторизацию и `config.toml` в смонтированном каталоге профиля, и они
  переживают перезапуски контейнера;
- `GH_CONFIG_DIR` — `gh auth login` в контейнере сохраняет токен в `.gh/` проекта;
- анонимный том поверх `.codex-accounts` и маска `/dev/null` поверх `.env` прячут от агента чужие
  профили и сам файл секретов.

В `.gitignore` проекта добавляются каталоги и файл с секретами:

```text
.env
.ssh/
.gh/
.codex-accounts/
```

### 2. Сгенерировать SSH-ключ

Ключ проекта лежит в `.ssh/` и монтируется в контейнер:

```bash
mkdir -p .ssh && chmod 700 .ssh
ssh-keygen -t ed25519 -N "" -C codex-box -f .ssh/id_ed25519
cat .ssh/id_ed25519.pub    # добавьте ключ в GitHub/GitLab
```

Чтобы контейнер использовал именно этот ключ, создайте `.ssh/config`:

```text
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    StrictHostKeyChecking accept-new
    UserKnownHostsFile ~/.ssh/known_hosts
```

Пути в `config` указаны так, как они видны внутри контейнера: каталог монтируется в `/home/codex/.ssh`.

### 3. Подготовить каталоги `gh` и профиля

Каталоги создаются заранее: отсутствующий путь Docker создаст от имени `root`, и агент не сможет
сохранить авторизацию.

```bash
mkdir -p .gh .codex-accounts/personal
```

Профиль — имя каталога внутри `.codex-accounts/`. Профилей может быть сколько угодно, имя
выбирается произвольно.

### 4. Запустить агента

```bash
CODEX_PROFILE=personal docker compose run --rm codex
```

Первый запуск попросит авторизоваться в Codex, авторизация сохранится в `.codex-accounts/personal`.
GitHub CLI авторизуется один раз из shell контейнера:

```bash
CODEX_PROFILE=personal docker compose run --rm codex bash   # shell в контейнере
gh auth login                                                # токен сохранится в .gh/
```

`CODEX_PROFILE` обязателен: без него compose остановится с ошибкой «не задан профиль аккаунта Codex».
При единственном профиле значение можно вписать в `.env` и запускать `docker compose run --rm codex`
без переменной.

## Переменные окружения

Задаются в `.env` проекта либо перед командой; значение перед командой перекрывает файл.

| Переменная | Назначение | По умолчанию |
|------------|------------|--------------|
| `CODEX_PROFILE` | каталог профиля в `CODEX_ACCOUNTS_DIR`, обязателен | — |
| `PROJECT_DIR` | каталог проекта внутри контейнера | `/app` |
| `CODEX_ACCOUNTS_DIR` | каталог профилей Codex на хосте | `.codex-accounts` |
| `CODEX_HOME` | каталог конфига Codex внутри контейнера | `/home/codex/.codex` |
| `SSH_DIR` | каталог ключей на хосте | `.ssh` |
| `GH_DIR` | каталог авторизации `gh` на хосте | `.gh` |
| `GH_CONFIG_DIR` | каталог конфига `gh` внутри контейнера | `/home/codex/.config/gh` |

Переменные `USER_ID`, `GROUP_ID` и `CODEX_VERSION` относятся только к
[локальной сборке](#сборка-образа) и передаются в `docker build` как build-arg.

## Состав образа

Базовый образ `node:22-slim`, глобально установлен пакет `@openai/codex`. Дополнительно:
`git`, `openssh-client`, `gh`, `ca-certificates`.

Другого агента, OpenSpec, Python и архиваторов в образе нет: пайплайн проверяет их отсутствие
перед публикацией.

## Сборка образа

Обычное подключение обходится готовым образом из GHCR. Сборка нужна в отдельных случаях:

- UID/GID хоста отличается от `1000:1000` — иначе созданные агентом файлы окажутся чужими;
- в образ требуются инструменты конкретного языка проекта;
- версия Codex закрепляется за проектом без опоры на теги реестра.

Образ собирается тем же `Dockerfile`, что использует CI, из клона этого репозитория:

```bash
docker build -f docker/codex/Dockerfile \
  --build-arg USER_ID="$(id -u)" \
  --build-arg GROUP_ID="$(id -g)" \
  -t codex-box:local .
```

Собранный тег подставляется в compose-файл проекта вместо образа из GHCR:

```yaml
    image: codex-box:local
```

Пайплайн [docker-codex.yml](./.github/workflows/docker-codex.yml) собирает и публикует образ в GHCR
для `linux/amd64` и `linux/arm64` при изменениях в `docker/codex/`, ежедневно по расписанию
и по ручному запуску. Публикуется только образ, проверенный на обеих архитектурах; запрос на слияние
образ собирает и проверяет, но не публикует.

### Версионирование образа

Собственной нумерации у образа нет: его версия — это версия Codex внутри него. Пайплайн получает
номер из npm до сборки, передаёт его build-arg `CODEX_VERSION`, сверяет с выводом `codex --version`
в собранном образе и публикует два тега:

| Тег | Значение |
|-----|----------|
| `<версия Codex>` | версия Codex, установленная в этой сборке образа |
| `latest` | последняя опубликованная сборка из ветки по умолчанию |

Актуальная версия — в бейдже **codex** в начале файла, история тегов — на странице пакета GHCR.

```bash
docker pull ghcr.io/united-software-platform/codex-box:<версия Codex>
```

При локальной сборке версию задаёт build-arg `CODEX_VERSION` (по умолчанию `latest` — актуальная
версия на момент сборки):

```bash
docker build -f docker/codex/Dockerfile --build-arg CODEX_VERSION=<версия Codex> -t codex-box:local .
```

Новая версия Codex подхватывается ежедневной пересборкой (`schedule`, 03:17 UTC): новые версии CLI
приходят из npm, а не из коммитов, поэтому push-триггеры их не видят.

> **Внимание:** тег версии не является неизменяемым. Ежедневная сборка при неизменившейся версии Codex
> перезаписывает и `latest`, и тег текущей версии — так в образ попадают обновления базового образа
> и системных пакетов. Для воспроизводимости образ адресуется по digest (`@sha256:…`), а не по тегу.

## Ограничения

- **Песочница Codex.** Сервис запускает `codex` без ключей, ослабляющих песочницу или подтверждения.
  Встроенная песочница Codex опирается на механизмы ядра, которые в контейнере Docker могут быть
  недоступны, — тогда команды агента завершаются ошибкой песочницы. Изоляцию в этом окружении даёт
  сам контейнер, и ослабить режим — решение владельца профиля: строка
  `sandbox_mode = "danger-full-access"` в `.codex-accounts/<профиль>/config.toml`. Допустимые ключи
  и значения — в документации Codex для установленной версии.
- **Вход в Codex из контейнера.** Вход через браузер ожидает ответа на локальном порту контейнера,
  недоступном браузеру хоста. Если вход не завершается, используйте способ входа без браузера,
  который предлагает `codex login --help` установленной версии.
- **Нет `docker` и `make`.** В контейнере нет средств виртуализации и сборки: команды `docker`
  и цели `make` выполняются на хосте.
- **UID/GID `1000:1000`.** В опубликованном образе они фиксированы. При другом UID хоста созданные
  агентом файлы окажутся чужими — нужна [локальная сборка](#сборка-образа).
- **Пакет GHCR приватный по умолчанию.** Новый пакет создаётся приватным: до первого `pull` нужен
  `docker login ghcr.io` либо публичная видимость пакета, которую выставляет владелец в настройках
  пакета.
- **Инструменты языка проекта** в образ не входят — их добавляют в `docker/codex/Dockerfile`
  и собирают образ локально.
- **Секреты.** Каталоги `.codex-accounts/`, `.ssh/`, `.gh/` и файл `.env` содержат секреты и должны
  быть в `.gitignore` проекта.
